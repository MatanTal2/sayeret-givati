# PWA shell (service worker)

**Files:** `src/app/sw.ts`, `src/components/pwa/ServiceWorkerUpdater.tsx`, `next.config.ts`
**Spec:** `docs/spec/offline-first.md` Phase 3
**Status:** Active

## What the SW does

- Precaches static build assets at install time (Serwist auto-injects the manifest).
- Runtime-caches API/page navigations via `@serwist/next/worker`'s `defaultCache`.
- Enables `navigationPreload` so first-paint while the SW boots is not blocked.
- Listens for `{ type: 'SKIP_WAITING' }` postMessage from the page and calls `self.skipWaiting()` only then.

`skipWaiting` and `clientsClaim` are both `false` at construction time. The SW
installs but waits. This is audit note **M5** in the migration spec — silent
activation can take over open tabs while optimistic state (P5) or
idempotency-bound mutations (P4) are in flight.

## Update flow (M5)

```
deploy new SW
   │
   ▼
page registers /sw.js
   │
   ▼
SW installs → state: 'installed' → fires 'updatefound' event
   │
   ▼
ServiceWorkerUpdater detects waiting worker → renders banner
   │
   ▼
user taps "Update now" → page posts { type: 'SKIP_WAITING' }
   │
   ▼
SW calls self.skipWaiting() → activates → 'controllerchange' fires
   │
   ▼
page reload (in onControllerChange handler)
```

User taps "Later" → banner hides locally, the waiting SW stays parked until the next page load picks it up again.

## Cache-Control on `/sw.js`

`next.config.ts` `headers()` returns `Cache-Control: no-cache, no-store, must-revalidate` for `/sw.js`. Audit note **S7** — if the SW JS itself is edge-cached for hours, the update never reaches users.

## Build output

- `public/sw.js` and helper chunks (`public/swe-worker-*.js`) are generated by `withSerwist` from `src/app/sw.ts` during `next build`.
- All SW outputs are gitignored.
- Dev mode (`process.env.NODE_ENV === 'development'`) disables the SW so HMR is not held back by a stale precache.

## Bundle budget

Phase 3 baseline (largest entrypoint, gzipped first-load JS): **93.56 KB**. Cap set to **110 KB** in `bundle-budget.json`. The SW itself is loaded out-of-band and does not count against this entry, but the registration glue (`ServiceWorkerUpdater`) adds a small amount.

CI step `build-and-budget` in `.github/workflows/ci.yml` runs `next build` with stub Firebase env vars then `npm run bundle-budget`. Phase 5 (outbox/replay) will bump the cap when it lands.

## Testing

Manual:
1. `npm run build && npm start`.
2. DevTools → Application → Service Workers — confirm `/sw.js` is registered and `active`.
3. Change anything in `src/app/sw.ts`, rebuild, reload — banner appears.
4. Click "Update now" — page reloads, new SW becomes active.
5. DevTools → Network → response headers for `/sw.js` → `Cache-Control: no-cache, no-store, must-revalidate`.

Playwright tests (M5 verification) wire up in Phase 5/8 when test infra for the SW lifecycle lands.
